# open-dot plan

## What it is

A durable personal agent, called a dot, built on OpenCode V2. Instead of a stream of disposable chats, you keep one continuing relationship. You give a dot a name and a purpose, reopen its conversation from anywhere, and it follows up on its own time. It remembers what you told it to keep and delegates substantial work instead of disappearing into it.

OpenCode provides the model, tools, permissions, chat and history. open-dot adds three things: identity, continuity and timing.

This project is a fresh, small rebuild of [open-bot](https://github.com/affddn/open-bot). It keeps the product direction from open-bot's issues and the OpenCode integration lessons, and drops the rest.

## Principles

- **Reuse OpenCode.** Don't add a second chat UI, agent loop, permission system or config language. Use only `@opencode/client` and `@opencode/plugin`, and never read or write OpenCode's database.
- **Attach, don't manage.** Connect with `Service.discover()`. Never start, stop or replace the user's service. Never call `location.reload()`, because it cancels work in other sessions.
- **Persist intent before acting.** Assign each `ses_` and `msg_` ID before the call that uses it. When an outcome is lost, reconcile it by that ID; never blindly send it again.
- **Report reality.** An admitted prompt has not completed, and an idle session has not succeeded. A state of _unknown_ is a real state, not an error to hide.
- **Treat outside content as data.** Connector messages and replies from other dots never carry authority.
- **Stay small.** Use one SQLite database, a handful of source files and a few focused tests.

## Architecture

```
~/.opendot/                              OPEN_DOT_HOME
  open-dot.db                            SQLite (Drizzle): dots, notes, memory_settings, archive, archive_cursors, memory_fts, reminders, responsibilities, responsibility_runs, run_workers, feed_triggers, trigger_occurrences, workers, requests, artifacts, outbox, feed, reactions, recent_reactions, hidden_messages, slack, slack_apps, slack_config, slack_events, slack_notices, slack_threads, slack_polls
  api.json                               the daemon's local API address and token, readable only by the owner
  dots/<name>/AGENTS.md                  the dot's personality and purpose (plain OpenCode instructions)
  dots/<name>/.instructions-history/     up to 10 earlier versions of AGENTS.md, kept by the notch's editor
  dots/<name>/avatar.png                 the dot's optional avatar, PNG or JPEG bytes
  work/<name>/                           the default directory for a dot's workers
  worktrees/<name>/<id>/                 the git worktree of a worker that runs in a repository
  outputs/<name>/<id>/                   a worker's own directory for deliverables, 0700
  library/<name>/                        private, immutable 0600 copies of the dot's Library, 0700
```

One `plugins` entry in the OpenCode config loads both plugins. The server plugin stays inert outside a dot's directory.

| Part          | Runs in              | Job                                                                                                                                    |
| ------------- | -------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| CLI           | `open-dot …`         | Create, list and open dots, and run the daemon.                                                                                        |
| Server plugin | OpenCode service     | Provides the tools a dot calls, such as `dot_remind`, `dot_track`, `dot_delegate` and `dot_message`. It writes only to open-dot's DB.  |
| Daemon        | `open-dot daemon`    | The single owner of timers, workers and the feed. It starts worker sessions, watches them, and sends every message through the outbox. |
| TUI plugin    | OpenCode terminal UI | Shows each dot and its recent workers in the sidebar and provides `/dot` and palette commands. It reads the DB read-only.              |
| Notch app     | `mac/`, a macOS app  | Sits at the notch. Hover to pick a dot, read and type to it, and see its workers. It talks only to the daemon's local API.             |

The daemon, not the plugin, owns timers for two reasons. A plugin runs only while its location is loaded, while the daemon can wake a dot whenever the OpenCode service is up. The daemon is also the host for the notch app and connectors, which is how you'll talk to a dot from anywhere.

The daemon serves a small HTTP API on `127.0.0.1` for the notch app, on a new port each start. It writes the address and a fresh random token to `api.json` with mode 0600, and rejects any request without that token, so other local users and web pages can't call it. `GET /dots` lists the dots, whether each is running a turn, its unfinished workers, and its `avatar`: null, or a `revision` that changes whenever the file is replaced or rewritten. `GET /dots/<name>/messages` returns the latest page of the dot's conversation, each message labeled as the owner's, the dot's, another dot's, or a notice such as a reminder or worker report. The label comes from the outbox row with the message's ID. A dot's messages show what it said and the open-dot tools it called, not mechanics such as shell commands, file reads or compaction. Each message lists its attachments as metadata only, `attachments: [{ index, mime, name }]`, with `index` the attachment's position in the OpenCode message. `GET /dots/<name>/messages/<id>/attachments/<index>` returns one attachment's bytes, from a message in that dot's own session, read with the public single-message API in `@opencode/client`. OpenCode keeps an attachment's bytes inline as base64, so nothing is read from a path or fetched from a URL. Only PNG, JPEG, GIF and WebP up to 10 MB are served, and only when the decoded bytes start like the claimed type, with `nosniff` and `no-store`. Other types get 415, data that isn't inline base64 422, a larger image 413, and a message or index the dot's session doesn't have 404. An optional `?sessionID=` pins the read: unless the dot is ready and bound to that session both before and after the history read, it gets 409, and a malformed value 400. Without it, the read uses the current binding, as older clients expect. The notch decodes only those four types, and shows other attachments by name. `POST /dots/<name>/messages` queues the owner's text in the outbox, marked as the owner's, and returns its ID with 202; the app never retries it on its own. An optional `feed` field, a feed item's integer ID, makes the text a reply to that item: the daemon reads the item from its own DB, never from the request, and an unknown ID gets 404. In one transaction it saves the outbox row with a snapshot of the prompt and item, and hands the item off to the dot: the item leaves the unread feed in the `handed-off` state and lists each dot it went to once. The message the dot gets is the owner's prompt, which is the only instruction, then the item as JSON in a `<feed-item>` block that says it's data from GitHub, Linear or Slack, with `<`, `>` and `&` escaped so a title can't close the block. Sending one item to several dots is one call per dot. The conversation shows such a message as the prompt and the item's card. Handing off doesn't mark an item read at its source; new activity on it brings it back unread with its dots kept. While OpenCode is down, every request except the feed's and memory's gets 503.

Conversation pages default to 20 messages, with `limit` from 1 to 50, in OpenCode's projection order, oldest first. The response includes `sessionID` and `next`; pass `next` unchanged as `before` for older history. The daemon wraps OpenCode 2.1.1's opaque cursor in a signed dot/session-bound cursor. Malformed or forged cursors get 400; an old binding gets 409. Restarting the daemon changes its token, so old cursors require Back to latest. A request reads at most ten upstream pages to skip mechanics; even an empty visible page can have a continuation. Hidden messages remain in pages for pending-send matching. The notch retains cached messages while refreshing, merges polls by ID, and publishes only changed windows. It holds at most 100 distinct message IDs per dot, including a latest-page cache: while reading older history it drops the newer end, and Latest messages restores the cached newest page immediately. Reaching that older window's bottom does not jump across missing history. At the actual latest bottom it drops the oldest end and keeps a cursor that can reread dropped history without gaps. Evicted or hidden thumbnails are freed, and late thumbnail reads cannot restore them. Older-page requests are session/cursor/write guarded. Reactions, hiding and attachments use public single-message reads, so they work outside the newest page too. After an uncertain mutation response, the notch reconciles the retained message through `GET /dots/<name>/messages/<id>?sessionID=<session>`. That read checks the binding before and after the public lookup and includes saved reactions and hidden state. Reconciliation keeps the intended value until it is observed, even if an early read precedes a late commit. Later polls attempt at most four reads in least-recently-attempted order; discarded targets or sessions end their checks. Mutations are never retried automatically. Native scroll stability and perceived latency still require manual acceptance.

While a message mutation is in flight or its outcome remains unknown, both Tapbacks and Delete wait for its saved state. Store guards also reject delayed menu or picker choices, so a new reaction cannot replace an unresolved hide or reaction. A mutation that never commits can remain blocked until its target or session is discarded; restarting the notch also clears this in-memory check. Discarding a check does not prove that the server request finished, so this is not an ordering guarantee across eviction or restart.

A dot's avatar is the optional file `dots/<name>/avatar.png`; it's personal data, never in the repository. Both the CLI and the daemon check an avatar's structure from its bytes, so the file may hold a PNG or a JPEG: at most 8 MiB, 128 to 4,096 pixels a side and no more than 10% from square. A PNG needs whole chunks with matching CRCs, IHDR first, image data, and IEND at the very end; a JPEG's markers are walked through every scan's data, past stuffed bytes, restart markers and fill bytes, to an end-of-image marker that must end the file, with exactly one frame header, before one or more scans, each with data. That reads no pixels. `open-dot avatar <dot> <file>` also has macOS decode the image: `sips` converts a private temporary copy of the bytes read to PNG, which must succeed at the same size, read from the output's header alone. Only an image the structure check bounded reaches `sips`. ImageIO may still render a JPEG whose scan data is damaged. The CLI then writes those original bytes to a temporary file in the dot's directory and renames it over `avatar.png`, so a refused or failed copy leaves the current one; the source is read once and never written. The authenticated `GET /dots/<name>/avatar` needs no OpenCode and serves only that exact file of a known dot with a valid name; any other name, including one that doesn't decode as a URL component, is 404. It opens the file with `O_NOFOLLOW`, refuses a link or non-directory at `dots/` or the dot's directory, before and after opening, requires a regular file whose inode still matches the path after opening, and applies the structure check, answering 404 for none, 413 when too large and 415 when broken. These checks narrow, but don't close, a race with a process that can already write to those directories swapping one for a link while the file opens. The notch downscales each revision once to 64 pixels and shows it in the dot's tab, which heads its chat, and beside the dot's own messages. It keeps an old image until a replacement loads, drops it at once when the file goes, and ignores a load whose revision is no longer current. A failed request, whatever the error, is retried on the next `/dots` poll; bytes that don't decode wait for a new revision. Without a file, the notch keeps its earlier stacks and alignment; nothing is added. Slack has no API for an app's icon, so `slack status` names the file to upload.

Chat reactions stay in open-dot's SQLite. Each row is keyed by dot, bound session, message ID and actor (`owner` or `dot`), with any single emoji, a 240-character excerpt read from authoritative history, and an update time. A single emoji is exactly one match of Unicode's `RGI_Emoji` property of strings, checked with Bun's `/^\p{RGI_Emoji}$/v`, so flags, keycaps, tag flags, skin tones and recommended ZWJ sequences pass, while text, unqualified symbols such as a bare ❤, lone regional indicators, several emoji and unrecommended ZWJ joins fail; Bun's bundled ICU sets the Unicode version (ICU 78, Unicode 17, in Bun 1.4.3). Removing a reaction stores a null emoji, so later context can explicitly report the removal. The authenticated, idempotent `PUT /dots/<name>/messages/<id>/reaction` accepts only `{ "emoji": <one emoji or null> }`, validates a visible assistant message in recent bound-session history, and returns `{ reaction, recentEmojis }`; repeating the same value preserves its timestamp. `GET /dots/<name>/messages` includes actor-labelled `reactions` on each message, including null tombstones, and `recentEmojis`. Each owner change to a non-classic emoji moves it to the front of `recent_reactions` in the same transaction, with a monotonic `seq`; only the latest five are kept, across dots, and they outlive the reaction's replacement or removal. A dot's reactions never count. `recentEmojis` is those five, newest first, with unused slots filled from 🧐 ✋ 👀 🧠 🔥 and no duplicates. Migration 0019 adds only that table. No reaction enqueues a prompt, synthetic message or Slack call.

Only the exact ready bound session may call `dot_react`, with the same single-emoji check as the API, and only for a real owner user message in the public `session.context` result. Outbox provenance excludes reminders, worker notices and peer messages using the same classification as the notch. The installed 2.1.1 plugin exposes `session.context`, not the client's paged message API. Fresh context advertises owner IDs from only the last 100 context items; the tool accepts an eligible owner ID anywhere in the current public context since compaction, and rejects targets absent from that context. Each normal context hook reads fresh reaction state: the latest 100 changed actor/message pairs, including removals, replace every older snapshot. State outside that window is explicitly unknown. Excerpts are JSON-escaped data, and feedback asks for no reply. Reactions are chosen only from a message's context menu. Mutations are serial per bubble; polls begun before or during a mutation cannot overwrite its confirmed result.

A secondary click or Control-click on a message's content opens a native AppKit context menu; the panel intercepts only those two events over a message, so ordinary clicks, text selection, links and thumbnails keep their handlers. The menu's first row is a macOS 14 inline palette of the six classic Tapbacks: standard menu items, so menu keyboard navigation, VoiceOver and the selected state work. A custom view in a menu item gets no key events. The second palette row is always exactly five: `recentEmojis`, or the same fill from 🧐 ✋ 👀 🧠 🔥 for an older daemon, then a smiley that opens the system emoji picker. When the owner's current reaction is in neither row, a separate checked "Your Tapback" item lists it, and choosing it removes it. The picker is AppKit's own `orderFrontCharacterPalette(_:)`, aimed at an invisible text view inside the message that becomes the panel's first responder once the app is active; its first insertion is the choice and goes to the menu's message, dot and session, never to whatever is selected later. AppKit offers no public way to close the picker or learn that it closed, so capture ends on the choice, Escape or another editing command, a non-emoji, or a minute without a choice, and the guard that follows is separate: once the picker has been shown, the view keeps the panel's focus and the notch's hold, dropping any later insertion, and nothing moves focus or folds the notch on its own. The guard and hold end only when focus really leaves the view (a click or Tab elsewhere, switching apps), the message leaves the panel, or another picker replaces it; a failed opening, or capture ending before the picker showed, releases the hold at once. A picker still open after the owner moves focus types wherever they put it, such as the message box's draft, never into a reaction. Overlapping reactions don't update the recent emoji from their responses; one fresh read after the last ends does. Each bubble also has a small ⋯ Message actions button, a standard SwiftUI button that Keyboard Navigation can focus, for example with Control-Tab out of the message box, and Space opens the menu. VoiceOver also has a "Message actions" action per message. The rest is Tapback Details, Reply, Copy, Share and Delete. Every action keeps the dot, message and session the menu opened for and refuses if they changed. Copy writes the plain text, or an image-only message's images as their original typed bytes. Share passes the text and every image to `NSSharingServicePicker`. Both load images again through the authenticated attachment API, pinned to the menu's session, and the same decode checks, cap at 10 images, and do nothing at all if one fails. A new share picker closes any earlier one. The notch stays open while a menu, alert, image load or share picker is up; a picker that AppKit never reports closed is closed after a minute, with a note saying so. A refused or failed action shows under its message, or above the message box once that message is gone or for a pending bubble, and is announced to VoiceOver. A pending bubble offers only text Copy, and Share when it has no images.

Delete hides a message in the notch only. The authenticated, idempotent `PUT /dots/<name>/messages/<id>/hidden` accepts only `{ "sessionID": <the bound session>, "hidden": true }` in at most 1 KiB, checks the exact ready binding before and after reading history, requires the message to be one `GET` would show and not a pending outbox row, and saves `(dot, session_id, message_id, hidden_at)` in `hidden_messages`; a repeat keeps the first time. `GET /dots/<name>/messages` gives each message its `sessionID` and `hidden`, keeps hidden messages so pending sends still match by ID, and answers 409 if the binding changed during its read. Only the notch filters them out. Nothing else reads the table: history, prompts, the outbox, reactions, quotes, attachments and the dot's context are unchanged, and a new session with the same message ID isn't hidden. Migration 0017 adds only that table.

The owner sees and edits a dot's memory in the notch's Memory view, without starting a turn: the dot sees the result in the memory snapshot of its next model request. A secondary click or Control-click on a dot's tab opens a menu with Memory and Instructions, each selecting that dot first; a plain click shows its chat. VoiceOver offers both as actions on the tab, and Command-1, 2 and 3 show the chat, Memory and Instructions while the notch has keyboard focus. Either view has a slim header with the dot's name, the view's name and a back control to the chat; Escape goes back too, unless an input method is composing text, and keeps any draft. `GET /dots/<name>/memory` returns the dot's `notes`, `responsibilities` (every active one, then the 50 most recently changed done or dropped ones) and scheduled `reminders`. Each item has `id`, `version`, `createdAt`, `updatedAt` and `updatedBy`: `dot`, `owner`, or `scheduler` when the daemon's schedule sent a reminder or moved a repeating one. `POST /dots/<name>/memory/notes` with `{ text }` adds a note and answers 201. `PATCH /dots/<name>/memory/notes/<id>` takes `{ version, text }`, `PATCH …/responsibilities/<id>` takes `{ version }` and at least one of `goal`, `nextAction` and `status` (`active`, `done` or `dropped`), and `PATCH …/reminders/<id>` takes `{ version }` and at least one of `dueAt` (integer milliseconds, in the future and within ten years) and `everyMinutes` (null, or 1 to 525,600). `DELETE …/notes/<id>?version=<n>` deletes a note and `DELETE …/reminders/<id>?version=<n>` cancels a reminder by deleting it, as `dot_cancel` does, both with 204. Text is trimmed, 1 to 2,000 UTF-16 code units, with no control characters except newline and tab; bodies are at most 64 KiB and may have no other keys. Malformed input gets 400, an oversized body 413, and an item that isn't this dot's, or no longer exists, 404. Each change is one conditional statement on the item's ID, dot and the `version` sent; if the item changed since then, or a reminder is no longer scheduled, nothing is saved and the answer is 409 with `current`, the item as it is now. The notch shows that value and never retries on its own; it also asks before deleting a note or cancelling a reminder, and an unanswered change is shown as unknown until a refresh. Responsibilities can't be deleted from the notch. These routes need the same token as the rest and don't need OpenCode.

`GET /dots/<name>/memory/search?q=<words>[&limit=<n>]` finds the dot's notes that contain every word, case-folded code point by code point: `q` is 1 to 200 characters after trimming, with at most 8 distinct words; tabs and newlines separate words like spaces, and any other control character is refused, and `limit` is 1 to 50, 20 by default; any other or repeated parameter is 400. It answers `{ query, results, more }`, most recently changed first, then newest ID, each result with `id`, `version`, `createdAt`, `updatedAt`, `updatedBy`, `source` and a `snippet` of up to 160 characters around the first match, never the whole text. An FTS5 trigram index, `memory_fts` (migration 0030), narrows the notes by their printable ASCII words of three or more characters, and each candidate's text is then checked word by word, so results are exactly the ones a scan finds; other words, such as ones with combining marks the index drops, never narrow it, and with no ASCII word it reads the dot's notes. Triggers on `notes` keep the index right for every writer, including a legacy plugin's inserts, edits and deletes, which show in the next search. It needs no OpenCode and starts no turn. Only the exact ready bound session may call `dot_search_notes` with the same rules; its results are escaped JSON framed as the dot's own saved notes, data that grants no permission. Note injection, versions and owner edits are unchanged.

A dot can keep an archive of its own conversation (#42, phase 1). It is off for every dot until the owner turns it on with the authenticated `PUT /dots/<name>/memory/archive`, which takes `{ archive?, backfill?, autoRecall? }`, booleans, at least one, in at most 1 KiB; `GET` shows the switches, `since`, the bound session, how many of its messages are archived, how many unfinished replies are watched and when the daemon last read. Neither needs OpenCode or starts a turn. While the archive is on, a daemon loop every 10 seconds reads the dot's exact ready bound session through OpenCode's public paged history (`message.list`, oldest first, 200 items a page, at most 10 pages a pass) and copies into `archive` only the dot's own assistant text and the owner's own words (the quote, feed or Slack prompt open-dot saved, else the message text), never reasoning, tool calls, attachments, notices or other dots' messages, with likely credentials replaced by `[redacted]`, best effort. Without backfill only messages from when it was turned on are copied; turning backfill on restarts the walk from the start, and the unique `(dot, session, message)` key copies nothing twice. Each page's rows and OpenCode's opaque cursor are saved in one transaction, only while the dot is still ready on the same session, its switches unchanged and the cursor row at the revision the read began from, so a restart resumes there and a rebind, switch change or concurrent pass saves nothing. A cursor that would loop fails the pass; an empty page whose anchor message is gone restarts the walk. An assistant message OpenCode hasn't completed is not copied yet; its ID is kept, however many there are, and read again by ID, 50 a pass with any still waiting moved to the back, until it completes or a later turn end shows it won't change. While 1,000 wait the walk pauses rather than drop any. A rebound dot starts a fresh walk of its new session, and its old session's rows stay but are never recalled. `memory_fts` indexes archived text too. Only the exact ready bound session may call `dot_recall`, which searches the dot's notes and, with the archive on, the bound session's archived messages for every word of three or more characters, best BM25 match first, 1 to 20 results a page (8 by default) with `offset` up to 200, each with an ID, date and a 160-character snippet, and each message with its `sessionID`, or `dot_zoom`, which opens one archived message of the bound session 4,000 characters at a time, with its `sessionID`. Words narrow recall when they keep three characters without combining marks. Both answer escaped JSON framed as recall data that grants no permission. Turning the archive off stops the reads and hides archived messages from both tools, and keeps the rows.

Automatic recall (#42, phase 2) is the dot's `autoRecall` switch, off by default (migration 0031 appends only `memory_settings.auto_recall`, false for every existing row). It acts only while both it and the archive are on; with the archive off it adds nothing, so behavior is today's, and `dot_recall` still searches notes. In the dot's context hook, after the public `session.context` read and the binding check that already follow it, the plugin takes the newest owner message since the last turn end in that context, by the notch's provenance and with the owner's own words; a turn with none, such as a reminder or worker wake or another dot's message, gets nothing. Its letters-and-digits words of three or more characters, less common English words, the longest twelve, are looked up in `memory_fts` with OR among the bound session's archived messages only, since notes are already in every memory snapshot. A hit needs a BM25 score of −2 or better, not yet calibrated on real use, and two of the words, or the only one; hits the current context shows are skipped, and at most three are kept. They are appended to the existing memory message, after the reaction snapshot, as `<recalled-context>` escaped JSON with each message's ID, `sessionID`, author, date, matched words and an excerpt, framed as data that grants no permission, and the whole block, escaping included, stays within 4,800 UTF-8 bytes, about 1,200 tokens, by shortening excerpts from 480 to 240 or 120 characters and then dropping hits. The block is computed once per owner message and reused, unchanged, on every later request of its turn, held only in the plugin's memory, never saved or logged. Nothing else in the request changes, no history is rewritten, and no model is called.

Each note has nullable `source_session` and `source_message` (migration 0025, which adds only those columns). `dot_note` now saves only from the dot's exact ready session, checked before the public plugin `session.context` read and again just before the insert, so a foreign, unready or rebound session saves nothing, even when the read failed. With the binding intact, the note gets `call.sessionID` and `call.messageID` as its source when that context lists the message as an assistant item, and no source when the read fails or the message isn't there, as after compaction. The model has no source argument. Old notes, the owner's and unconfirmed ones are unknown, `source: null`. Edits never change the source; `source.edited`, which is `version > 1`, says it shows only where the note was first saved, and no source is ever proof that a note is true. The authenticated `GET /dots/<name>/memory/notes/<id>/source` needs OpenCode: it answers 404 for a note this dot doesn't have, `{ note, state: "unknown" }` without a source, 409 when the dot isn't ready, `state: "unavailable"` with a `reason` for a source in an earlier session, which is never read, and otherwise reads the message with the public single-message API from the exact bound session, checking the binding again once connected to OpenCode, before the read, and the binding and the note after it: 409 if the binding changed, 404 if the note went, 503 if OpenCode failed, `state: "gone"` if OpenCode has no such message, else `state: "found"` with `edited` and `message: { id, sessionID, role, text, truncated, tools, time }`, the text cut at 4,000 characters. The notch's Memory view has a search box above the notes; it shows only the newest search, drops an answer begun before or during any memory change and runs the search again once the change settles or a refresh shows different notes, and removes a deleted note at once. **Source** shows the message as plain text, as data; an answer for another message or session is refused, and an open or in-flight source read is dropped once a save, a conflict or a refresh shows its note at another version or with another source, or without the note, and whenever a conversation read shows a session other than the one the notch last knew, including the first one it learns, so a source read before then is never left shown. A running OpenCode keeps its loaded plugin, so the tool and source capture reach a dot after OpenCode loads the plugin again.

Migration 0020 adds `version` (default 1) and `updated_by` (default `dot`) to `notes`, `responsibilities` and `reminders`, and a nullable `updated_at` to `notes` and `reminders`, where null means unchanged since `created_at`. Only the owner's API and the daemon's schedule advance `version` themselves. An `AFTER UPDATE` trigger on each table catches every other update, which leaves `version` unchanged: it advances the version, stamps the time and records `dot`, or `scheduler` for reminders. So a plugin still running code from before the migration, whose `dot_update` knows nothing of versions, still makes the owner's stale edit a conflict. Its inserts get the column defaults. The daemon claims a due reminder only at the version it read, and advances it in the same statement, so a reminder the owner changed or cancelled after that read is neither sent from it nor overwritten; the next tick reads it again.

A responsibility may have a `schedule`, saved as JSON: `{ kind: "interval", everyMinutes }` (1 to 525,600), `{ kind: "daily", time: "HH:mm" }` or `{ kind: "weekly", days, time: "HH:mm" }`, with days 0 (Sunday) to 6, each once, sorted on save. `dot_track` takes an optional schedule; `dot_update` takes one too, where null removes it and omitting it keeps it. `next_run_at` is the next due time of an active scheduled responsibility, and null otherwise. Writers compute it in the same write: a new or changed schedule, or a status set back to active, starts at the first run after now; an unchanged armed schedule keeps its run; done or dropped clears it. Daily and weekly times are local to the system time zone, read each time a run is computed, never configured. A local time skipped by a DST jump runs as far past the jump as it was past its start (02:30 becomes 03:30), a repeated local time runs only at its first occurrence, and an interval counts real minutes, not wall-clock time. Each tick the daemon claims every active scheduled responsibility of a ready dot whose run is due, at the version it read and advancing it, moves `next_run_at` to the first run after now and queues one wake in the same transaction, with a fresh `msg_` ID like a reminder's. The wake is unrouted, so it reaches only the dot's chat, and carries the goal and next action as they are at the run. So a restart before or after the claim sends each run once, a lost admission is reconciled by ID, and runs missed while the daemon was stopped wake the dot once; an interval steps from its last due time, a daily or weekly one from now. A responsibility of a dot that isn't ready stays due and wakes it once when it is. Migration 0021 adds the nullable `schedule` and `next_run_at` columns, so old rows have no schedule, and a `responsibilities_pause` trigger that clears `next_run_at` whenever any update sets the status to done or dropped and leaves it set, as a plugin from before the migration does. Such a plugin reopening it leaves `next_run_at` null, and the daemon arms a null run from now without sending anything, so a resume never catches up and an old writer can't leave a paused schedule armed or a resumed one unarmed. 0020's version triggers are unchanged. The owner's status edits in the notch pause and resume the same way, in one immediate transaction at the version the owner saw, and the daemon's claims advance the version, so an edit loaded before a run is a conflict. `GET /dots/<name>/memory` gives each responsibility its `schedule` and `nextRunAt`, and the notch shows them; the owner API and notch don't edit schedules. Repeating reminders are a separate mechanism and are never converted.

Each scheduled run the daemon claims is saved in `responsibility_runs` (migration 0027, which adds only that table and `run_workers`) in the same transaction as the claim and its wake: the run's own due time, the claim time, a snapshot of the goal, next action, schedule and version it read, the dot's session the wake went to and the wake's saved `msg_` ID. A failure saves none of them, a catch-up after downtime is one run that keeps its original due time, and DST handling is unchanged. Arming a null run, feed trigger wakes and reminders record no run, and no run is ever made up from `next_run_at` or older wakes. While a run's wake is admitted and its turn not seen to end, a daemon loop of its own reads where it is every five seconds through the public client, the session's inbox before its history: `queued` in the inbox, `running` in a turn with no idle yet, with whether the session waits on a permission or question, then `ended` with the idle's outcome, error and time, or `missing` when it's in neither, or OpenCode says the session is gone. History pages follow OpenCode's `next` cursor whenever one is given, end when none is given or a page is empty, and fail on a cursor given twice or past 5,000 pages rather than loop or read as absent; this walk also serves worker reports and Slack replies. A read that fails changes nothing. Each change is saved only while the run is still open, so restarts at any point resume from what was saved. An ended turn is `shared` once history shows any other input in it, counting user, synthetic and shell messages since the idle before it. It is `exclusive` only when history also shows that idle and nothing in the turn was compacted, so the whole turn is in sight, and its one input is the wake: then its last assistant text (600 characters) is the run's result. Anything else, such as a turn whose start is out of sight or behind a compaction, is `unknown`. Neither shared nor unknown gets a result. The plugin's `dot_delegate` saves a `run_workers` row only when public `session.context` shows the idle before the invoking assistant message's turn, nothing compacted in that turn, and exactly one input in the whole turn as far as context goes, including anything already after the invoking message, that run's wake in the same session. The reminder and worker reply-route rules are unchanged. An older plugin, until OpenCode reloads it, saves none. A link is provisional while the run's turn runs, since later input can still join that turn: the run shows such workers marked provisional, then as its own once the turn ends exclusive, and withholds them, showing only how many, once it ends shared or unknown or goes missing. The authenticated, read-only `GET /dots/<name>/memory/responsibilities/<id>/runs[?before=<run>]` pages a responsibility's runs 20 at a time, newest first, with `next`; another dot's responsibility is 404 and any other parameter 400. It needs no OpenCode and starts nothing. Each run has its `state`: `queued` until OpenCode admits the wake, `admitted`, `running`, `needs-you` while its turn waits on a permission or question or a worker it delegated needs the owner, `finished-turn` when the turn ended, which never means the goal was met, `failed` when it failed or was interrupted, or `unknown` when it's missing. It also has its delivery, turn, attribution, result, `withheldWorkers` and the delegated workers it shows, each with its state, outcome, needs and `provisional`, so a worker's later report shows on the run as evidence, never acceptance. In the notch's Memory view each responsibility has Show runs, which loads the newest page and refreshes with memory, and Load older runs. Each showing is its own opening, so answers to reads begun before a hide change nothing, and a slower answer moves neither the older-page cursor nor the error past a later one. Each run shows its evidence as plain text: Show prompt, and Show result once a result is attributed, read the message once through the existing pinned `GET /dots/<name>/messages/<id>?sessionID=<run session>`, which says when the message is gone or the run's conversation is no longer the dot's ready one, and Open session for its workers. Nothing reruns, retries or notifies.

The owner can also bind a responsibility to GitHub feed activity with a feed trigger (migration 0026, which adds only the `feed_triggers` and `trigger_occurrences` tables). Only the owner's authenticated API makes one: `POST /dots/<name>/memory/triggers` with exactly `{ responsibility, repository, reasons, task }` saves a draft for an active responsibility of that dot, bound to the dot's ready session at that moment, with `repository` as GitHub's `owner/name`, lowercased, `reasons` one or more of the feed's GitHub labels (Review requested, Mentioned, Team mentioned, Assigned, Comment, Author), each once, and `task` the owner's instruction, checked like memory text. A dot has at most 20 open triggers. Nothing else changes a trigger's dot, responsibility, session, repository, reasons or task; to change one, revoke it and make another. Its `revision` is the SHA-256 of that fixed configuration. `GET …/triggers/<id>/preview` lists up to 20 saved feed events its filter matches, newest first, each with what it did or would do, and the exact text a wake about the newest would carry; it only reads, so it claims, queues and calls nothing. `POST …/triggers/<id>/enable` with exactly `{ revision }` enables a draft or resumes a paused trigger, only for the revision on the row, which must still hash its configuration, only while the dot is ready in the same session and the responsibility is active; otherwise 409 with `current`. `POST …/triggers/<id>/pause` pauses an active one and `DELETE …/triggers/<id>` revokes any. `GET …/memory` lists draft, active and paused triggers as `triggers`, each with its last wake (events and delivery: `queued`, `sending`, `admitted` or `cancelled`), how many were baselined and skipped, and the five latest skips. No model tool creates, enables or changes a trigger, and feed text can't: a dot may suggest one in prose for the owner to make.

Each enable or resume bumps the trigger's `epoch`, sets `baseline_at` to now and records every activity its filter already matches as `baseline`, in one transaction, so neither a backlog nor a feed poll that began before it, whose activity is older, ever wakes the dot. An occurrence is keyed by trigger, source, the feed item's `sourceID` and its `updated_at`, never by poll or title, so repeated polls and restarts add nothing while later activity on the same item counts again. Each second the daemon matches every active trigger's filter against its saved feed, by source `github`, the item's lowercased repository exactly and its reason, past `baseline_at`, and in one transaction claims the new activity and queues one unrouted wake with a fresh `msg_` ID: a failure saves neither. A wake carries at most five events, oldest first, and a trigger queues at most three wakes in a rolling hour; the rest, and any activity while the dot is bound to another session or isn't ready, or the responsibility is done or dropped, are saved as skipped with a reason and never run, so reopening a responsibility or resuming a trigger doesn't replay them. Paused and draft triggers aren't matched at all. The wake text is open-dot's headline, the owner's saved instruction unchanged, then the events in `<feed-events>` as JSON with `<`, `>` and `&` escaped, framed as GitHub's data that can't change the trigger, its instruction or its destination. It goes through the outbox like any notice, so it never reaches Slack and makes no external call. Pausing or revoking cancels its wakes the daemon hasn't started, and the delivery gate checks, before starting a wake and again after the by-ID lookup just before the prompt, that its trigger is still active in the same epoch, bound to that exact ready session, and its responsibility active; a wake that fails is cancelled, unless OpenCode already has its ID, which then stays sent. So a wake started before a pause, whose outcome was lost, is never sent after a resume. In the notch's Memory view, Responsibilities ends with Feed triggers: each shows its repository, reasons, responsibility and exact instruction, its last wake, skips and session. New feed trigger… opens a form whose Save Draft only makes a draft. Preview shows the matching saved events and the exact wake text as plain text. Enable… and Resume… show the exact filter, destination, instruction and the start of the revision, and send that revision; Pause…, Revoke… and Discard… ask first too. Nothing is retried on its own.

The owner reads and edits a dot's `AGENTS.md` in the notch's Instructions view, or in an editor at the path `open-dot instructions <dot>` prints. The authenticated `GET /dots/<name>/instructions` returns `{ content, revision, canRevert }`, where `revision` is the SHA-256 of the file's bytes and a missing file reads as empty. `PUT` with exactly `{ content, revision }` replaces it, and `POST …/instructions/revert` with exactly `{ revision }` puts back the newest earlier version and drops it from the history, so each revert steps one version further back; the text it replaces isn't kept, and the notch asks first. Both answer the new `{ content, revision, canRevert }`, and both answer 409 with `current`, that same object for the file as it is now, when the revision isn't the one on disk; saving the same text is a no-op. The notch offers Reload, which drops the draft, or Overwrite, which saves the draft again at the conflict's revision, never without one, and shows the file's current text; a refused revert offers only Reload. It never retries on its own. Its Instructions view has a monospaced editor with its own undo, Save, Cancel and Revert. The draft stays in the notch's memory while the notch folds or another dot or view is shown, and the dot's tab and its menu's Instructions item are marked while it has unsaved edits; Cancel, Reload and Revert ask before dropping them, and quitting the notch asks while any dot has some. One request runs at a time per dot. Meanwhile the draft takes no edits: the state refuses any change until a file is loaded and while a request runs, the editor puts a refused change back, and its undo and redo are disabled and do nothing while it's read-only. After an unanswered save the draft stays: saving it again is safe, since the daemon refuses a stale revision, and a refusal whose current text is exactly the draft counts as saved. Content is well-formed text without NUL, at most 64 KiB of UTF-8; bodies may be six times that, for JSON escapes. Only exactly `dots/<name>/AGENTS.md` of a known dot with a valid name is read or written, never the directory the database names. `dots/` and the dot's directory must be real directories, and `AGENTS.md` a regular file opened without following a link whose inode still matches the path; otherwise every route gets 422. Once those pass, a stale revision gets 409 before anything else. A `.instructions-history/` that exists but isn't a real directory makes `GET` answer 200 with `canRevert: false`, and a save or revert 422, except a save of the same text, which changes nothing. Inside the history only regular files named by number count as versions; links, other files and other names are skipped. A file over the limit gets 413 and bytes that aren't UTF-8 422, whether `AGENTS.md` or the version a revert would put back. A save first copies the old text to the history as the next numbered file, `000000000001.md` and up, then writes the new text to a temporary file in the dot's directory, syncs it and renames it over `AGENTS.md`; a failure before that rename removes the copy and the temporary file and leaves `AGENTS.md` as it was. Only the newest 10 versions are kept. Pruning, and a revert's removal of the version it put back, happen after the rename and are best effort: a failure is logged and the change stands, so the history may hold more than 10 until a later save prunes it, or a later revert may put the same text back again. The history is only files, so it survives a restart. The check, copy and rename run synchronously, so two requests in the daemon can't both pass the same revision; a process writing the file directly can still race the rename. Nothing here needs OpenCode or starts a turn. In OpenCode 2.1.1 the instruction plugin (`packages/core/src/config/plugin/instruction.ts`) watches each `AGENTS.md` it loads, through its parent directory, so a rename counts; 100 ms after the last change it reads the files again and reloads instruction discovery, and the session's context uses the reloaded instructions from its next model request. The notch says: "OpenCode watches this file. After it reloads (normally shortly after saving), edits apply to the next model request, including during a running turn. No restart is needed." The instructions the plugin adds each turn stay in the plugin, never in `AGENTS.md`.

The daemon also collects the feed: once a minute it asks GitHub and Linear for the owner's unread review requests, mentions and assignments, plus GitHub activity on threads the owner opened or commented on, and Slack for mentions of the owner and DMs to them, from the last 24 hours, which costs no model tokens. GitHub uses the token of the `gh` login and Linear a personal API key from the Keychain item `open-dot-linear`; both stay in memory. A notification read at its source leaves the feed at the next pass. `GET /feed` lists the unread items, oldest first, and the 20 most recently active handed-off items with the dots each went to. `POST /feed/<id>/dismiss` hides one at once, and the daemon marks it read at its source on its next pass; new activity brings it back, as it does on GitHub. The notch's Clear all, shown above the unread items, sends one `POST /feed/dismiss` with `{ ids }`, the unread IDs shown at the click (1 to 1,000, each once), never a server-side clear of everything, so items that arrive meanwhile stay. Each known ID is dismissed exactly as a single dismissal would be, so a handed-off one is unchanged, and the answer lists `dismissed` and `missing` IDs; a storage failure saves none. There is no confirmation or undo, since a dismissal is not a deletion and can't take back a read at the source. The notch hides the items at once and brings back each one not dismissed, with its error, never retrying on its own. Only the newest feed poll is used, and a cleared item stays hidden until a poll begun after the clear succeeded, so an older poll can neither bring it back nor drop a failure shown since. A dot reads the feed with `dot_feed`, framed as data from GitHub, Linear and Slack.

Each `GET /feed` snapshot contains at most the oldest 1,000 unread items. The notch also bounds the actual displayed list to 1,000 after merging polls and restored failures; overflow stays in memory with its errors for the next snapshot. The button shows an “at least” remaining count using the larger of the server count and local overflow, since those sets may overlap. After a clear, the notch refreshes to show the next items; it never silently truncates the IDs submitted by a click. The `dot_feed` tool is not limited by this display bound.

The owner talks to dots in Slack through a DM with an internal Slack app, which the daemon polls every 3 seconds over the Web API: no public URL, events or Socket Mode. Its bot token and the owner's user token live in the Keychain items `open-dot-slack-bot` and `open-dot-slack-user` and stay in memory. Chat requires the owner's user identity and a checked bot in the same workspace. Only the owner's human messages instruct a dot. Each message is saved in `slack` with its outbox row in one transaction, deduplicated by Slack timestamp. A leading dot name on a top-level message selects the dot; otherwise the previous dot in that DM is used. A known thread stays pinned to its original dot and session, regardless of a later name prefix. Unknown threads do not route implicitly. Replies post under the original root timestamp with a saved reply ID in metadata. Unknown threaded posts are looked up with `conversations.replies(include_all_metadata=true)` and exact bot and reply IDs; legacy top-level unknowns use history. Empty or failed reads never permit replay. A 429 pauses calls until `Retry-After` passes.

Shared ingestion reads at most one top-level history page plus one page each from four distinct known threads per pass, with 100 messages requested per page. `slack_polls` saves the history watermark and a JSON continuation containing Slack's cursor and pending owner messages. Slack's newest-first pages are accumulated before oldest-first routing. `slack_threads` saves the exact route, root quote, oldest/newest timestamps, cursor, rescan flag, last owner activity and poll order. Threads active within seven days, with a nonempty cursor, or marked for rescan are visited least-recently-polled first. An invalid cursor is atomically cleared with `rescan` set, preserving activity and watermarks. Only a successful page transaction clears the flag; its continuation cursor keeps an unfinished scan eligible. A monotonic persisted poll order breaks same-millisecond ties. Page ingestion and cursor updates are transactional. Old inactive threads remain pinned but are not polled forever. Authentication, sends and metadata reconciliation are outside the five-page ingestion bound.

For the feed, the user token's `search.messages` finds mentions and DMs, filtered again locally, and a DM is dropped once `conversations.info` shows it read. A title shows Slack links by their label, the owner's mentions by the handle from `auth.test`, and others' by the name `users.info` gives, or their user ID while it can't. `users.info` needs `users:read`, so it isn't called once a response's `x-oauth-scopes` header shows the user token lacks it. Without that header the lookup is tried, and its `missing_scope` drops the token like any other, pausing Slack until the Keychain is read again a minute later. Dismissing a Slack item changes nothing in Slack.

A dot can also have its own Slack app, so it has its own name, profile and agent view, and an @handle that works in any channel it's invited to. The shared app stays for the feed and its DM. Once the owner runs `open-dot slack notices enable`, it also tells anyone else who DMs it, once, that it only answers the owner: once a minute it lists every DM the bot has with `conversations.list`, page by page, and reads the ones whose sender it hasn't told, from the time saved in `slack_config` when notes were turned on. So DMs sent while the daemon was stopped count, and older ones never do. Until then, and after `open-dot slack notices disable`, it makes no call for this at all. `open-dot slack connect <dot>` only records a request in `slack_apps`; the daemon creates the app. It does so with the owner's app configuration token, which lasts 12 hours, so it's rotated with `tooling.tokens.rotate` before each use. The rotation is saved as started in `slack_config` before the call, and the new pair goes straight into the one Keychain item `open-dot-slack-config` through `security -i` on stdin, never argv or a log. A rotation whose answer or save is lost blocks all later ones until the owner saves a new pair with `open-dot slack config`, since Slack may have used up the old refresh token. The rotation's answer must name the owner and workspace of `open-dot-slack-user`. The app's attempt is saved before `apps.manifest.create`, and only its public app ID is kept. A lost answer makes the app _unknown_, never created again on its own: the owner either names the app with `open-dot slack attach <dot> <app ID>`, which the daemon checks with `apps.manifest.export` (its bot must be named after the dot and use Socket Mode), or confirms there is none with `open-dot slack connect <dot> --retry`. Slack sends an install's OAuth code only to HTTPS, so the owner installs the app and saves its bot token and an app-level token with `connections:write` in `open-dot-slack-<dot>-bot` and `open-dot-slack-<dot>-app`; `open-dot slack status` gives the steps. Before any other call, the bot token's `auth.test` must show a bot in the owner's workspace, `bots.info` must show it belongs to the dot's app, and once saved, the same bot and bot user. That saved identity is read at every check, so a token read again later in the same daemon can't belong to another bot, and a connection's `hello` never replaces it. Each create or attach saves its own attempt ID, and its outcome is saved only while the app still has that attempt and app ID, so a late answer about an earlier attempt changes nothing. A check that fails means the call it guarded was never sent, so it's retried later, never treated as a write that may have happened. The app-level token opens a Socket Mode connection, whose `hello` must name the dot's app before the app becomes active.

Each event's `api_app_id` and `team_id` must match the app. The daemon saves it in `slack_events` before acknowledging it, keyed by app and event ID and by app, channel and `ts`, so a redelivery under either adds nothing. It keeps only the fields it needs, never the envelope's verification token, and the text only of the owner's messages. A new owner event without a ready dot binding or checked app identity is not acknowledged. Only the owner's own human messages from the owner's workspace instruct a dot. Each channel mention gets a reply in its thread, even when several mentions share a turn. Thread messages are read across all pages, from after the context of the last confirmed mention reply, and supplied as escaped JSON data. A thread that cannot be fully read queues nothing. Top-level DMs use their own timestamp as root; in-thread DMs retain their root, and same-thread messages sharing a turn get one reply. Root quotes come from Slack, never from a model. Someone else's mention or DM reaches no dot; they get one saved, at-most-once ephemeral note per conversation and person. Reply ID, text and destination are saved before posting. Per-dot unknown posts are looked up once a minute for an hour per runtime, with exact bot and metadata IDs, and never resent. Only a confirmed reply moves mention context forward.

A dot's own app also behaves like an agent in Slack; the shared app doesn't. The oldest waiting owner message of each thread whose prompt is in the session's history carries the turn's live state. On a DM thread the daemon saves `status_at`, then calls `assistant.threads.setStatus` with "is thinking…", again each minute while the turn runs and nothing streams. Once the message is no longer waiting, because its turn ended, it clears the status with an empty one, unless another waiting message in the thread holds its own; a cleared or abandoned row nulls `status_at`, and Slack drops a status after two minutes anyway. While the turn runs, public `message.list` gives the turn's assistant messages after the prompt, each with its text parts; OpenCode 2.1.1 writes a part's text there only once it ends. For the text in between, `slackAgents.events`, one more daemon fiber, follows the public `client.event.subscribe()` stream only while some dot's own app is active, and is interrupted when none is. It keeps only `session.text.started`, `delta` and `ended`, never reasoning or tool events, and only for sessions with a waiting Slack row, keyed by assistant message ID and ordinal, at most 64 parts per session and 12,001 characters each, one past Slack's 12,000 so a part too long to stream still reads as too long. A part counts only if this connection saw it start, since the stream has no replay, and everything kept is cleared on each connect, end or failure, after which it reconnects 5 seconds later. The fiber only buffers; the 3-second tick alone reads and calls Slack. A carrier's text is, for exactly the assistant messages history shows in its turn, each part's history text once finished and otherwise its live text, joined; so a gap only delays text until history has it. Rows are read one at a time, so a turn can end between two reads: a later DM in a thread whose earlier message still looked unfinished waits a pass instead of replying alone, since a later message's turn can't end before an earlier one's; and if any DM in a thread can't have its history read, none of that thread's finished messages reply that pass, since the unread one may share their turn. A later message read fine but unfinished is in a later turn, so it never holds an earlier reply back, and other threads go on. open-dot never reads OpenCode's database. The first nonempty text starts `chat.startStream` after saving `stream = starting`, a fresh `stream_id` and the text; its chunks are a section block whose `block_id` is `open-dot-stream-<stream_id>`, then the markdown. Slack's `ts` makes it `open`. A start that was never sent is cleared; a known refusal is `denied`, which falls back to one `chat.postMessage` at the turn's end; a lost one stays `starting` and is only looked up with `conversations.replies`, by that exact block ID on the dot's own bot's message, once a minute for an hour, never started again and never replaced by a post. Later texts that extend `stream_text` are appended after saving `appending`; a confirmed append saves the new text, a lost one makes it `broken`, and a row left `appending` by a stopped daemon becomes `broken`, so nothing is ever appended twice. When the turn ends, a streamed row carries its group's reply, and the whole group moves in one transaction, so a crash can't leave a row to make a second reply. It's stopped with `chat.stopStream` and no text, which is repeated after a lost answer since stopping twice only says `message_not_in_streaming_state`; then, marked `unknown` first, `chat.update` with `as_user`, one markdown block of up to 12,000 characters and notification text clipped to Slack's 4,000 replaces the message with the turn's canonical reply and its reply-ID metadata. A lost update repeats the identical call once a minute for an hour; `streaming_state_conflict` stops it again first. Mentions keep one reply each, and only the thread's oldest waiting mention streams, with the owner and workspace as the stream's recipient. `assistant_thread_started` and `app_home_opened` on the Messages tab from the owner are saved as `prompts` events, without the thread's context, and answered once with `assistant.threads.setSuggestedPrompts` with `channel_id` and no `thread_ts`, which an agent view app's call silently ignores: the owner's saved `slack_apps.prompts`, set with `open-dot slack prompts`, or two plain prompts and the purpose. After a DM thread's first confirmed reply its `title`, the owner's first 60 characters there, is saved before the one `assistant.threads.setTitle`; a call never sent is retried, any answer is final, and later rows of the thread are marked untitled. Migration 0024 adds only nullable columns to `slack_apps` and `slack_events`, and marks old DM rows' titles empty so their threads keep their names.

New apps get manifest version 2, which subscribes to `assistant_thread_started`, `assistant_thread_context_changed` and `app_home_opened`. An older app is updated only on the owner's word, never by the daemon on its own: `open-dot slack update <dot>` at a terminal, or Update in the notch's Slack view, whose daemon route runs the same code, answers first with the changes it would add and sends nothing until the owner approves exactly those. It rotates the configuration token for the app's saved owner and workspace, exports the app's manifest, checks its bot is named after the dot and uses Socket Mode, and adds only the missing bot scopes and events to the exported manifest, because `apps.manifest.update` replaces the whole manifest. It shows what it adds and asks for a yes, then saves `update_state = updating` before the call. Every move of an update is conditional on the state and `update_at` it was read with, and stamps `update_at` past the last one, so a stale export or a late answer about an older attempt never overwrites a newer one. Success saves the version, and `permissions_updated` saves the reinstall step that `slack status` shows. A refusal is `failed`. A lost answer is `unknown`, and is never resent: the next update exports the manifest again, and if nothing is missing it records that the update landed, with a possible reinstall, and otherwise asks before sending a fresh one. Slack's `apps.icon.set` sets an app's icon: a multipart `POST` with `app_id` and `file`, a user token with `app_configurations:write`, Tier 1, and 512 to 2000 pixels a side. Whether Slack takes open-dot's app configuration token for it is unproven until the owner tries it.

When a dot's app is `created` or `active` and the dot has an avatar whose revision (#30) isn't the one saved in `slack_apps.icon_revision`, the daemon's 10-second setup pass, after creating and attaching apps, reads the avatar's checked bytes while its revision stays the same, rotates the configuration token for the app's saved owner and workspace as above, saves `icon_state = setting` with the revision in `icon_attempt`, and sends the bytes as `file`, the token in the `Authorization` header. Success saves the revision. `ratelimited` saves `waiting` until Slack's whole `Retry-After`, at least a minute, however long, up to the latest time `Date` can show, and that deadline holds every app's icon call, whatever avatar it has by then; once it passes, the call is sent again, since Slack refused it. Any other refusal is `refused` with its error code. A lost answer, or an error after which Slack may have done it, is `refused` with `unknown_outcome`, and a `setting` left by a stopped daemon becomes the same a minute later, unsent: Slack can't be asked what icon an app has, so such a call is never sent again on its own. A refusal of either kind waits until the avatar's revision changes or the owner presses Retry icon in the notch, which is refused while a call is in flight or the rate limit holds. At most one `apps.icon.set` a pass, and none within a minute of the last move of any app's icon. Every move is conditional on the `icon_state` and `icon_at` it was read with and stamps `icon_at` past the last. A new app ID, from a retried create or an attach, clears what was known about the icon. No app or no avatar means no call and no Keychain read. `slack status` and the notch say where the icon stands; after a refusal, such as `not_allowed_token_type`, `missing_scope` or `invalid_icon_size`, or an unknown outcome, they name the code and give the Display Information upload steps with the avatar's path. `open-dot avatar` warns when an image is outside 512 to 2000 pixels. Migration 0029 adds only nullable `icon_*` columns to `slack_apps`.

Slack's answers to the configuration API are untrusted. Only an error code on a fixed list of Slack's documented codes is saved, logged or shown, and any other is `slack_error`; Slack's own `errors` messages are never kept. An app, team or user ID is saved or printed only in Slack's form (`A…`, `T…` or `E…`, `U…` or `W…`), so a create whose answer has no such app ID is `unknown`, a rotation naming other IDs blocks, and its message says "an unrecognized ID". A setup failure that isn't open-dot's own words is saved as fixed words. A bot token's check, `auth.test` and for a dot's app `bots.info`, and the owner's user token's `auth.test` pass on only such a code too, and a bot or owner whose user, bot or workspace ID isn't of Slack's form is never kept, logged or connected. A bot or app-level token whose save can't be read back is reported as unconfirmed, since it may have been written; the notch says Not confirmed.

The owner's save of a configuration pair, from the CLI or the notch, and a rotation both write `open-dot-slack-config`, so both claim the same `rotating` state, and every move of either, by a rotation, a save or a recovery, is conditional on the state, `updated_at` and `from_iat` it read. A rotation claims only from the idle row it read before reading the pair, so a save in between stops it before Slack is called; it renews its claim just before saving its rotated pair, and if the claim was taken over meanwhile, or is gone when it ends, it saves nothing more and uses no token. A save claims from `idle`, `blocked` or a claim over a minute old that a stopped process left, and is refused while one runs; the notch's route answers 409. A saved pair ends as `idle`. A save that isn't confirmed fails closed: the item may hold either pair, so the row is `blocked` until the owner saves again. A save's claim has `from_iat` -1, and its pair carries the claim's time as `saved`, so one a stopped process left counts as finished a minute later only when the item holds that very pair; otherwise it's `blocked` too, since the item may still hold a pair whose refresh token a lost rotation used up. This fences open-dot's own processes within the Keychain calls' 10-second limits, not a process suspended for over a minute or another program writing the item.

Installing still needs the owner's Install and Allow in Slack, and Slack has no API for app-level tokens, so the notch makes each step one click away. The notch sends anything to the daemon, its token always and these secrets too, only when api.json names plain `http` to `127.0.0.1` or `[::1]` with a port and no user, path, query or fragment; through no proxy; and never on through a redirect, which it treats as no daemon.

Every daemon prompt goes through `outbox`. Its producer persists a fresh `msg_` ID in the same transaction as its state change. A common FIFO gate groups work by session across both Slack connectors, native messages, peers and notices. It records `started_at` before lookup/admission, reconciles a lost admission by ID, and records `turn_end` only from authoritative public turn completion. An admitted ID is not completion. Different routes cannot enter together; contiguous same-route messages may fold until another destination is queued. Missing or failed history does not release the gate. A session running a turn that open-dot didn't start holds a pending Slack-routed row, and everything behind it, until that turn ends; unrouted rows ahead of it, such as the owner's native messages, still enter that turn. Threads never create dot sessions or a native thread list.

They reject unavailable, compacted or mixed origins and recheck the exact ready binding after the await. A newer queued message cannot replace that origin. Later native turns have no route. The model has no destination argument.

Delayed work posts the persisted notice, not the dot's later response. The worker transition or reminder occurrence transaction queues both the chat notice and one Slack intent. DM-origin notices retain the original connector and thread; channel-origin notices go only to the original app's owner DM. Identity or session replacement blocks delivery rather than redirecting it. The chat notice itself is unrouted, preventing a second Slack answer. Non-Slack workers keep the existing active-dot-app DM report behavior. Old rows with null origin never acquire an invented thread. Migration 0015 adds route/quote/delivery fields and polling tables, preserves existing columns and rows, and initializes old sent rows for conservative public-history reconciliation.

Supplied quote text has no authority. GET shows the snapshot even after the parent leaves recent history. When the gate admits an auto row, the daemon chooses `steer` only if public `session.active` lists the session and its public inbox holds no `queue` item, otherwise `queue`, and saves the choice with `started_at` before the lookup and prompt. A lost outcome is looked up by ID and, if absent, sent again with the saved mode. So a message in history has been delivered; nothing public reports whether a model request with it succeeded, so there is no Read. The notch shows those labels and Delivered under a trailing owner message. Migration 0018 adds only nullable `outbox.delivery`; old rows stay queued.

Native chat keeps stable-ID images and 160-pixel thumbnails per dot. Editor paste and drop retain their originating dot. A worker is a top-level OpenCode session, because a child session cannot have its own directory. `dot_delegate` saves the worker and its `ses_` ID. The daemon creates the session with the model the dot's session has then, or OpenCode's default when it has none, queues the task, tells the dot once about each pending permission or question so it can answer it, and queues one report when the first turn after the task goes idle.

Each pass, the daemon reads a running worker's pending permissions (`permission.list`) and questions (`session.form.list`) through the same `waiting` call supervision uses. Each new one gets a row in `requests` (migration 0023, which adds only that table), keyed by session, kind and request ID, with what OpenCode showed: a permission's action, resources and message, or a form's title and full fields, keys and options. The same transaction queues one notice to the dot, with that detail as escaped JSON framed as the worker's data, so a restart tells nothing twice and one that goes and comes back is never told again. Keys an older daemon saved in `workers.waiting_on` are saved without a notice. A request OpenCode stops listing, or whose worker finished, is marked gone, never answered. A form whose words or metadata suggest a secret (password, token, key and the like), or with an external field, is kept as a fixed redacted title with no fields, metadata or words of its own, in the database, the notice and supervision notices alike; it goes straight to the owner, and nothing answers it.

The dot answers with `dot_permission` (once or reject), `dot_question` (a reply checked against the fields, or reject, which cancels the form) and `dot_escalate` (with a reason). The answer's shape is checked at runtime by the tool, when it is queued and again before it is sent, so always, or anything but `{decision: "once"|"reject"}`, `{decision: "reply", answer}` or `{decision: "cancel"}`, never reaches OpenCode. Each works only from the dot's exact ready bound session, on its own open request. A supervised session is refused: any `supervisions` row for that session, by any dot, whose state isn't `ended` (so `requested` or `active`); send mode is never ownership. The tool only saves the answer, the dot session and the time on the row and moves it to `queued`, once: a request takes one answer. The daemon alone replies, from one answer loop, inside the session's gate, the same one stops use; a gate held by an admission or a stop only skips that pass. It first reads the session's pending list, then, for a Threads worker, a fresh Threads snapshot for the answering session, each within 10 seconds; one that fails or times out sends nothing and escalates once, so a queued answer never waits forever. With no await left, it checks that the dot's binding is still ready and the answering session, that an open-dot worker is still the dot's and running, that a Threads worker is in that snapshot under that exact coordinator and in the directory first seen, that no supervision row is open, and that the request still waits with the same detail. It saves `answering` with the attempt time before its one call, `permission.reply` with `decision: "once" | "reject"`, `session.form.reply` or `session.form.cancel` from the installed 2.1.1 client, and `answered` with the confirmation time after. A request gone first, or a worker stopped, is `stale`; any other failed check refuses the answer and escalates. A failed call, one taking over 30 seconds, or an `answering` row a restarted daemon finds, is `unknown`: never sent again, never inferred from the request disappearing. The tool waits up to four seconds and says whether OpenCode confirmed the answer or it's only queued. A permission open-dot recognizes as off limits can be rejected but not approved: deleting outside the worker's own worktree (the one open-dot made for a worker with a branch; a scratch-directory or Threads worker has none, so no deletion is approved, and a command that changes directory first counts as outside), force pushes, resets and history rewrites, merges, deleting branches, `~/.config/opencode`, merging or readying pull requests, requesting reviewers, publishing, deploys, Slack, Linear or Notion, or a bare `*`. It's a conservative pattern check that a command can get around, not a sandbox. The policy is in new dots' AGENTS.md, in the tool descriptions and in each turn's memory, since existing AGENTS.md files are never rewritten; it says a request's text, or anything a model writes, is never the owner's consent.

The owner is needed when an answer's outcome is unknown, or when a request still waiting was escalated by the dot or by open-dot, or went two minutes from first sight without an answer. Each queues exactly one unrouted message in the dot's chat, so nothing reaches Slack, and an escalated request can't be answered by the dot afterwards. An unknown answer stays unresolved and needs the owner even after the request leaves OpenCode or its worker finishes; nothing marks it resolved, and the audit keeps it. `GET /dots` gives each unfinished worker its `state`, `needs` (the kinds that need the owner now), `waiting` (the kinds its dot is handling) and `answered`, a few words about the dot's latest answer, and each dot `sessions`: every Threads session waiting on something, and any session, Threads or a finished worker's, with an unknown answer. The notch marks rows that need the owner and counts them on the dot's tab. The read-only `GET /dots/<name>/requests[?before=<id>]` pages through the dot's requests 100 at a time, newest first by ID, with `next` for the older page, each with its OpenCode request ID, detail, complete answer, `detailText` and `answerText` (that detail and answer as indented JSON), answering session, state and times, kept after workers finish. The notch's Memory view lists them, expands each to its complete request and answer, and loads older pages; a slow read never replaces a row a later read set.

Worker requests run in their own loops beside the worker, supervision and delivery pass (`daemonLoops`), each on its own fiber, so a poll that fails or never answers, such as `session.active`, a pending list or a stuck admission, holds up neither. A local loop, every second and touching only the database, needs no OpenCode, not even finding the service: it marks requests of finished workers gone, makes any `answering` row this process isn't sending `unknown`, and escalates once a request still waiting past the two-minute grace and an answer still `queued` a minute after the dot chose it. The answer loop connects only when an answer is queued, and sends them one at a time, so none is sent twice; every change on either side is conditional on the state it read. An answer in flight is never marked unknown by the local loop; its call's 30-second limit settles it.

A Threads worker counts as the dot's only when Threads' public `threads` RPC `snapshot`, called with `client.rpc.call` in the dot's directory with `coordinatorIDs: [the dot's session]`, lists it with exactly that `coordinatorID`; the payload is schema-checked, and an unavailable or malformed snapshot means no detection and no answer. `snapshot` delivers no follow-ups; `restore` is never called. The daemon reads it every five seconds for each ready dot, each read within 10 seconds, skipping hidden workers and sessions that are an open-dot worker or a dot, and saves what it found only if the dot's binding is still ready and the same after its reads. Threads workers get the same detection, answers, audit and needs-you, but open-dot never takes over their lifecycle: `GET /dots` lists them under the dot's `sessions`, the notch's row opens the session with `POST /requests/<id>/open`, and stopping stays in Threads.

`POST /workers/<id>/open` opens a worker's session in a new terminal window, from the worker's directory, with `<binary> -s <sessionID>`. The binary is `OPEN_DOT_OPENCODE`, `opencode2` by default. The terminal is `OPEN_DOT_TERMINAL` (`ghostty` or `terminal`), else Ghostty when `/Applications/Ghostty.app` exists, else Terminal. The daemon runs `osascript`, passing the directory and the shell-quoted command as arguments, never as script text: Ghostty gets `new window with configuration {initial working directory, initial input}`, and Terminal a `do script`, so the owner's own shell and PATH run it. Those terms come from Ghostty 1.3's `Ghostty.sdef` and Terminal's `Terminal.sdef`; neither has been run live. Ghostty's AppleScript also needs `macos-applescript`, which is on by default. If that fails, or takes over 8 seconds, as when macOS Automation permission is missing, the daemon copies the command with `pbcopy` and answers `{ opened: false, copied, command, error }`; the notch shows it. A worker still creating has no session yet and gets 409.

`POST /workers/<id>/stop` stops a worker after one confirmation in the notch. OpenCode keeps queued input parked after an interrupt without resume, and promotes it on any later wake, so the stop must keep open-dot from waking the worker. Every admission into a session, and every stop of the worker in it, runs one at a time behind that session's in-process gate. Inside it the stop first saves the worker as `stopping` and marks every pending outbox row for its session `held`, in one transaction, then calls `session.interrupt` with `resume: false`. So an admission already in flight finishes before the interrupt, and one that read its row before the stop finds it held and sends nothing. Only once OpenCode confirms does a second transaction make the worker `done` with the outcome `stopped`, and queue one notice to its dot. A finished turn of a stopped worker reports nothing more. A held row is never looked up or sent on its own, even one whose earlier outcome was lost. A failed or lost interrupt leaves the worker `stopping` and its rows held, answers 502, and is never retried by the daemon, even after a restart, because a blind retry could stop a worker the owner has since resumed; only the owner's next stop tries again. Stopping a stopped worker changes nothing and answers 200; a worker that finished on its own gets 409. Only a pending `dot_send` queued after the stop, whose watch-and-send binding is still active for that dot and session, is explicit. Held rows never count, so an older held `dot_send` can't resume the worker, even on a binding that is still active. A held row stays `held` until OpenCode confirms it: it's taken in line, in its original order, only while a later pending `dot_send` exists, and is admitted only with a permit, the first such `dot_send` its binding still allows. Inside the session's gate, the daemon saves `started_at` on the held row, looks it up by ID, and checks the same permit again just before the prompt, after every await. Only a confirmed admission, by ID or by the prompt, turns it `sent`. A lost admission leaves it held, with `started_at`, and it's looked up again only under a new permit, never retried on its own. A revoked permit sends nothing and is itself cancelled as before. Any other row queued for a stopped worker is held, not sent. A message the owner types in its session resumes it in OpenCode the same way, with what OpenCode parked; open-dot doesn't track a resumed worker. Both routes need the API token.

A worker given a directory inside a git repository gets its own worktree, so workers never share a checkout. `dot_delegate` records the repository and a new branch, `dot/<name>-<id>`, in the same transaction that saves the worker. Before creating the session, the daemon adds the worktree from the repository's current HEAD. If git can't add it, the worker ends as failed and the dot gets one report. Worktrees are kept after the worker finishes, so its branch can be reviewed or merged; remove them with `git worktree remove`.

Each worker gets its own output directory, `outputs/<dot>/<worker id>/`, made 0700, with `outputs/` and `outputs/<dot>/`, by `dot_delegate` when it saves the worker; its path depends only on the worker's row, never on a model, and it's never shared with another worker or the scratch directory. The `dot_delegate` answer and the worker's task name it, and the task asks the worker to save file deliverables there and name them in its summary. Only the dot's exact ready session may call `dot_library_add` with a worker number and a path, which adds that file to the dot's Library. The worker must be the dot's own, by its `workers` row, and the session saved with the deliverable is that row's. The path is relative to that worker's output directory, or absolute inside it, at most 1,024 characters and 16 parts of up to 255 bytes, with no empty, `.` or `..` part and no colon, backslash or control character, so no URL is ever read or fetched.

Library file access runs only on macOS on Apple silicon; elsewhere adding is refused and copies read as corrupt. `OPEN_DOT_HOME` is opened by path, following links above it, which are trusted but checked: it must be the owner's and writable by no one else, and each directory above it root's or the owner's and writable by no group or others unless sticky. open-dot never changes their modes. Below it, every operation goes through a directory descriptor already opened and checked, with libc's `openat`, `mkdirat`, `mkostempsat_np` and `fdopendir` through `bun:ffi`, never through a path, so renaming or replacing a directory with a link, even away and back, can't redirect it: a link where a directory or the file is expected is refused, and one swapped in after that directory was opened isn't seen. Each directory open-dot manages (`outputs/`, `outputs/<dot>/`, the worker's output directory, `library/` and `library/<dot>/`) must be the owner's and exactly 0700, and each the worker made the owner's and writable by no one else; a missing managed directory is made 0700, and nothing else is changed. The file is opened without following a link or blocking on a FIFO and must be the owner's regular file with exactly one link, so it can't be a second name for a file elsewhere. It's read once, in 64 KiB chunks, only while its device, inode, size, links, mode, owner and nanosecond change and status-change times are the same before and after, so a write during the read, even one that keeps its size, refuses it. Only `.txt`, `.md`, `.markdown`, `.csv` (UTF-8 without NUL) and `.pdf` (starting `%PDF-`) files are taken, each at most 10 MiB. A dot's Library holds at most 200 deliverables and 200 MiB in all, counting both its rows and every file physically in `library/<dot>/`, whichever is more, so a copy a crash left without a row, or a row whose copy is gone, still uses up the caps; anything there but the owner's private regular file with one link stops adding until it's removed. That scan stops once the caps are reached, so planted files can't make it read more than 200 entries, and a listing that fails part way, which only errno tells from its end, refuses the addition. Inside one immediate SQLite transaction, which makes competing plugin processes take turns, the caps are checked, a new copy is created exclusively, 0600, under a random 32-character name, written, synced with its directory, checked again (still that private file with one link, holding exactly the bytes read, under its name in a directory still at `library/<dot>/`) and only then published by inserting its `artifacts` row (migration 0028, which adds only that table) with the name, type, size, SHA-256, creation time, worker, worker session and path. A failure rolls the row back but never deletes the copy, since by then its name might be another file: the copy, like one a crash leaves, stays as an orphan that counts against the caps until the owner removes it. open-dot never deletes a file in the Library. Nothing ever changes or deletes a published copy. The same bytes from the same worker and path again return the first deliverable; the same name from another worker or with other bytes is a separate one.

The authenticated, read-only `GET /dots/<name>/library[?before=<id>]` pages the dot's deliverables 50 at a time, newest first, with `next`, each with `status`: `present` when its copy is there, the owner's private file with one link and of the saved size, which isn't a digest check, `missing` when it's gone, or `corrupt` for anything else wrong with it or the directories above it. `GET …/library/<id>` reads the copy and says `verified` only when its SHA-256 matches; `GET …/library/<id>/content` serves the bytes only then, as `application/octet-stream` with `Content-Disposition: attachment` and a safe ASCII file name plus the exact UTF-8 name, `nosniff`, `no-store` and a sandboxing CSP, answering 410 for a missing copy and 422 for a corrupt one. Reads go through descriptors the same way, refusing a copy whose name in the database isn't one open-dot makes. Another dot's deliverable, any other path or method is 404. None of it needs OpenCode or starts a turn. In the notch, Library is the third item of a dot tab's menu, after Memory and Instructions; it lists the deliverables with their type, size, worker and status, loads older pages, and Export… reads the bytes by ID, refuses any whose size or SHA-256 isn't what the list showed, and writes them where the owner chooses in a save panel, never opening them. Nothing is retried on its own. Image attachments are unchanged.

Dots message each other with `dot_message`. Each dot's memory lists the other dots and the purpose each was created with. The plugin inserts the message straight into the outbox, addressed to the other dot's session and recorded with the sender, and the daemon delivers it like any other message. The message is framed as data from another dot, not instructions from the owner, and asks for no reply that only acknowledges or thanks. To stop two dots from keeping each other busy, a dot can send at most 10 messages per rolling hour, counted from the outbox.

A dot can supervise an OpenCode session the owner started. A binding in `supervisions` (migration 0022) holds the dot, the `ses_` ID, the directory OpenCode reports for the session, the mode (`watch`, or `send` to also write into it), a busy threshold in minutes (30 by default), and its creation and activation times. Only the owner makes a binding active: `open-dot watch add <dot> <ses_…> [--send] [--busy-minutes N]` or `open-dot watch approve <id>`, each asking for a yes at a terminal, or Approve in the notch's Memory view, which asks first. `dot_watch` only saves a `requested` row, after reading the session's directory through the public plugin API, and the dot is told nothing is watched until its owner approves; a model's say-so never activates anything. The owner ends a binding with `open-dot watch revoke <id>` or Revoke and Decline in the notch, and `dot_unwatch` lets a dot end its own, from its own bound conversation only, as with `dot_watch` and `dot_send`. A failed session lookup in `dot_watch` says so and saves nothing; only OpenCode's typed not-found answer is reported as a missing session. The notch row shows the session, directory, mode, threshold, and when the binding was requested, or created and approved. The terminal prompt and the notch's bearer token are same-user trust boundaries: they keep a dot's own tools from activating a binding, not a dot that runs arbitrary local commands as the owner. At most one requested or active binding exists per dot and session. Each turn, the memory snapshot lists the dot's requested and active bindings, and `GET /dots/<name>/memory` returns them as `supervisions`; `POST …/memory/supervisions/<id>/approve` and `DELETE …/memory/supervisions/<id>` change them without starting a turn.

On each pass the daemon looks at every active binding of a ready dot. A session OpenCode reports as not found ends the binding as `deleted`, with one notice; a failed lookup changes nothing. Turn ends come from public `message.list` filtered to `idle`, newest first, page by page down to the binding's `seen_at`, however many there are; a cursor OpenCode returns twice fails the pass rather than looping or skipping. `seen_at` is the creation time of the newest turn end reported, and `seen_ids` the IDs reported at exactly that time, so another turn end in the same millisecond is still reported once. Activation sets `seen_at` with no IDs, and only later turn ends count, so turns that ended before the binding, or in its activation millisecond, are never reported, and ones that end while the daemon is down are, all of them. Each new turn end is reported as idle with its outcome and the first 600 characters of the newest assistant text in that turn. Only when there are new turn ends, assistant messages are paged the same way and matched by creation time: a turn's reply is the newest text strictly after the previous turn end and strictly before its own. A text in the same millisecond as a turn end may belong to either neighbouring turn, so a turn with any text exactly at its own end gets no excerpt, rather than an earlier reply passed off as its last; a turn with nothing strictly inside gets none either, or as failed with its error. Pending permission requests (`permission.list`) and questions (`session.form.list`) are reported once per kind and ID, and the reported IDs are kept after they're answered, so one seen again is never reported twice. A turn running longer than the threshold, measured from when the daemon first saw it busy, is reported once per busy spell. The cursor, the reported IDs and the busy state are saved in the same transaction that queues the notices, through the outbox like every other prompt, and that transaction finds nothing to do once the binding has ended. A notice is open-dot's own headline followed by the session's content as JSON, with `<`, `>` and `&` escaped, inside `<supervised-session>`, framed as data and never instructions. It reminds the dot never to answer the session's permissions or questions; open-dot has no code that answers or interrupts a supervised session.

On a watch-and-send binding, `dot_send` puts one outbox row into the supervised session, recorded with the dot as sender and the binding, labelled as from the dot rather than the user and counted toward its 10 messages an hour. It is queued by default, or with `steer` uses the native "auto" choice: steered into a running turn with no queued input ahead, otherwise queued. The daemon checks that the binding is still active, in send mode, for that dot and session, before saving `started_at` and again after the by-ID lookup, just before the prompt; a row whose binding ended is marked `cancelled` and never sent. A started row with a lost outcome is looked up by ID: if OpenCode has it, it was admitted before the revocation and stays sent; if not, it is cancelled rather than resent.

Dot and worker sessions are created with `ask` rules for destructive shell commands, such as `rm`, force pushes and hard resets. Everything else follows the owner's OpenCode permissions, which allow all by default. The list is best effort: a pattern list can't catch every destructive command. A worker's asks go to its dot first, which answers only within the policy above and escalates the rest.

The TUI plugin imports no backend code: no `@opencode/client` and no Drizzle. open-bot found that these imports break plugin loading.

Its sidebar shows up to 10 workers per dot: all running workers first, newest by creation time, then the most recently finished within 24 hours. More than 10 running workers all remain visible, with no finished rows. A muted `… N more` row opens a selector for all of that dot's recent workers; a selection opens the same details as a worker row. The sidebar still refreshes every two seconds and skips unchanged snapshots.

`open-dot doctor [--json]` and the authenticated `GET /health` give one read-only report, `{ schemaVersion: 1, checkedAt, sampledAt?, sampleUnavailable?, checks }`, each check with `id`, `status` (`disabled`, `not_configured`, `healthy`, `stale`, `failed` or `unknown`), `summary` and, when useful, `nextStep`, `lastSuccessAt` and `counts`. `checkedAt` is when the report was made; `sampledAt`, present only when the database checks come from a snapshot, is when that snapshot was taken. `sampleUnavailable`, never with `sampledAt`, says why a daemon has no usable snapshot: `missing`, `expired` or `failed`. Every timestamp is a positive integer of milliseconds that `Date` can represent, at most 8.64e15. The CLI runs before anything opens the database, so it migrates nothing and works with the daemon stopped. It reads `api.json` and sends its token only to plain `http` on `127.0.0.1` or `[::1]`, never following a redirect, and waits at most five seconds: a missing file, nothing answering, a 401 or a redirect each say the daemon isn't running or the file is stale. A database snapshot is the migration ledger's comparison with the code's migrations by time and hash, then, only when it matches exactly, the dots' session bindings, the delivery counts and the Slack counts, all read with SELECTs in one deferred read transaction, so they agree; pending, unknown, changed or skipped migrations are counted and no other table is read. The daemon takes one at start and then from its existing one-second tick, at most every 15 seconds, and pins it. A failed attempt marks the sample failed until the next successful one; it keeps the last snapshot and its `sampledAt` internally but shows none of it. `GET /health` only reads that pinned sample and never touches the database: with no snapshot yet (`missing`), one over a minute old or ahead of the daemon's clock (`expired`), or a failed latest attempt (`failed`), the report has `sampleUnavailable` and no `sampledAt`, every database check is unknown with fixed words and no counts, and no saved session is read. The CLI never opens the database file with SQLite. Only when no `-wal`, `-shm` or `-journal` file shows a connection may hold changes the file lacks does it copy the file, at most 256 MiB, into memory, refusing a copy whose size, inode or change times moved during the read, and take its snapshot from that copy with `Database.deserialize` read only, after `PRAGMA quick_check`. That copy is as current as the file, which with no WAL file holds every committed change; it's no guarantee against a writer starting during the read beyond those checks. While a connection holds the database, as the daemon and OpenCode's plugin do, the CLI reports it unknown and shows the running daemon's snapshot checks instead, only when that report's `sampledAt` is at most a minute old and not ahead of the CLI's clock by more than five seconds; an older or later one is shown as `expired`. A daemon's `sampleUnavailable` reaches the CLI's report as itself, with the CLI's fixed words for that reason. The CLI makes every daemon check again from its id, status, allowlisted non-negative integer counts and, for feeds, a `lastSuccessAt`; any other field or malformed value, a `sampleUnavailable` with a `sampledAt` or outside the three reasons, or, without a `sampledAt`, any database check that isn't unknown or carries counts rejects the whole report, and the daemon's words are never shown. OpenCode is found with `Service.discover()`, which never starts a service, then read only with `server.info` and `session.get` for each ready dot's saved session; nothing is ensured, stopped, reloaded or prompted. Discovery, the info read and the session reads share one three-second deadline, inside the CLI's five-second wait for the daemon's report; the deadline interrupts reads in flight, no read starts after it, and an unread session is unknown. Sends are counted with the existing states: outbox rows pending and unstarted are queued, started ones unknown, and Slack's `waiting`, `posting` and `new` rows queued, its `unknown` rows and notes still `sending` unknown. Slack apps are counted by saved state and whether a problem is saved, never its words; any problem, a failed app or a blocked configuration token fails, and a saved `active` is unknown, since no connection is observed here. Notes to others turned on are unknown too, and off is `disabled`. Each points to `open-dot slack status`. The daemon's feed loop records each source's last finished pass in memory: a pass that read the source, one without credentials, or one that failed; never item activity. These reach the CLI only through a running daemon's report and are unknown otherwise. No check repairs, retries, backs up, migrates, installs, reads a Keychain item or controls a worker or service, and no report carries a name, token, path, session or Slack ID, message text or raw error; a failed `GET /health` logs only fixed words. The notch shows the daemon's report under Health, the fourth item of a dot tab's menu, with when it was checked and sampled, or why there's no sample, and Check again.

## Conversation reads

The daemon keeps the latest conversation page per dot in memory, bound to its session and requested page size. It prewarms ready dots after startup. A warm read returns without waiting for OpenCode; a cold read shares the one refresh already in flight. Refreshes take at most 20 seconds. Requests reuse the public client instead of rediscovering the service each time. The cache keeps upstream text and attachment metadata, never image bytes. Every response rereads local outbox provenance, pending sends, hidden state and reactions, and checks the session binding again. Older cursor pages still read OpenCode directly.

The background loop checks each second without waiting for another dot's read. A recently viewed dot refreshes two seconds after its last successful read; other dots wait 30 seconds. The existing Slack text-event subscription invalidates a page when a text part ends, with a short delay for a recently viewed dot. No extra event subscription or Slack call is made for chat caching. A disconnected stream, or one inactive because no Slack app is active, relies on the background fallback. Failures back off from two to 30 seconds and keep the last good page with a refresh error. A rebound session never reuses the former session's page. No conversation cache is written to disk.

The notch serializes latest-page reads per dot, coalescing overlapping triggers into one follow-up read instead of discarding every slow answer. It shows loading before the first page and an error with Retry on failure, keeping any messages already shown. A non-visible dot is swept every 30 seconds independently of the five-second feed poll. Decode failures log only the response type, field path and failure kind, not payload values. Mutation and per-message reconciliation guards still apply.

## Verified OpenCode behavior

These were checked live against OpenCode 2.1.1 and shape the code:

- **A repeated prompt ID is deduplicated.** Calling `session.prompt` twice with the same `msg_` ID returns that ID both times and leaves one message in history. The daemon's resend-if-absent step relies on this, but still checks by ID first because a concurrent race was not tested.
- **Per-request context goes near the tail.** Memory pushed onto `system` in the `context` hook was fresh in every request, yet the dot kept answering from its first turn's memory. Like OpenCode's own Plan reminders, memory is now a user message placed just before the latest prompt. That also keeps the cached prompt prefix stable.
- **Session permissions come after the agent's.** Rules passed to `session.create` are merged after the agent's rules, and the last match wins. Saved "always allow" approvals come after both.
- **A finished turn ends in an `idle` item.** `session.context` lists it with an outcome of `succeeded`, `failed` or `interrupted`. Message IDs don't sort in processing order, and `session.context` starts at the latest compaction. To find a prompt's turn, the daemon therefore walks `message.list` forward (`order: "asc"`, then each page's `next` cursor) and takes the first `idle` after the prompt. `session.active` lists only running sessions, and `permission.list` lists a session's pending requests.
- **TUI imports need explicit extensions.** OpenCode maps `@opentui/solid` and `solid-js` to its own copies only in local files it can resolve without adding an extension. The root `tui.ts` therefore imports `./src/tui.ts`. Without the extension, the sidebar loads a second Solid and crashes with "No renderer found".

## Milestones

Each milestone is a shippable vertical slice, tracked as a GitHub issue. Verify each one once, when it's complete.

1. **A dot you can open.** Build the scaffold, the DB, `open-dot create|list|open`, and a durable session binding: create the session once with a pre-assigned ID, then reconcile it by ID. Add the TUI sidebar, `/dot` and palette entries. Reopening a dot keeps its history, and a missing binding produces a clear error, not a replacement session.
2. **It follows up.** Add the `dot_remind` and `dot_note` tools and the daemon. Due reminders are queued into the dot's session with deterministic `msg_` IDs. Reminders survive a restart, and an unknown delivery is reconciled by ID, never duplicated.
3. **It delegates.** Add responsibilities, each with a goal, a next action and a status. The dot hands substantial work to worker sessions, tracks them, and brings a linked summary back into its conversation. It also gets a simple recurring schedule.
4. **Dots talk to each other.** Several specialist dots can message each other, and replies are treated as untrusted data.
5. **Talk to it from the notch.** The daemon serves a small local API, and a thin native macOS app talks to it. Hovering over the notch opens a panel where you pick a dot, read its conversation, type to it, and see worker results arrive.
6. **A feed in the notch.** The daemon collects what needs your attention from GitHub and Linear, such as review requests, mentions and assigned issues, and the notch shows it as a live, Twitch-style stream you can act on. Feed items reach a dot only as data.
7. **Slack.** DM an internal Slack app to talk to a dot, and it replies there under its own name. Only the owner's messages instruct a dot there. Your Slack mentions and DMs join the notch feed as untrusted data. Each dot can also get its own Slack app that you mention in any channel.

## Deferred or dropped

- **Deferred:** rich goal and planning views, voice, native mobile and remote executors.
- **Dropped:** open-bot's governance control plane, coordinator ownership epochs, workflow VM, duplicate chat UIs, Python fixtures and vendored lint plugins.

## Decisions

- **The client is a thin native macOS app in the notch,** not a web client. It holds no state of its own and talks only to the daemon. It comes before Slack.
- **The first notch version shows the notification feed as well as dot chat.** The feed shows things that need your attention, not every event.
- **Slack does two jobs:** it's a way to talk to your dots, and a source the dots watch for you.
- **Dots run only on this Mac for now.** An always-on host can come later.
- **A dot may do anything except destructive actions without asking,** like Grok Bot, Codex or pi-durable. Destructive actions, such as deleting files, force pushes or hard resets, still ask: the owner in a dot's own session, and the dot first in its workers' sessions, which may allow only what fits the worker's task, such as deleting inside its own worktree, and hands the rest to the owner.
